## 為什麼是 Apps Script 不是別的

| | Apps Script | Supabase / Firebase |
|---|---|---|
| 費用 | 0 | 免費額度夠，但要開帳號綁卡 |
| 資料在哪 | 你自己的 Google 試算表，隨時打開來看 | 要進後台查 |
| 你要維護什麼 | 一張試算表 | 一個專案、一組金鑰 |
| 上限 | 每天腳本執行時間 90 分鐘（約 3,000～4,000 次呼叫） | 高很多 |

測驗站的量級用 Apps Script 綽綽有餘，而且**你隨時可以打開試算表看到名單**，
不必再問我。這一點比效能重要。

## 設定步驟（大約 10 分鐘）

### 1. 開一份試算表

Google 雲端硬碟 → 新增 → Google 試算表。命名例如
`SPOTIME 測驗站資料`。

網址長這樣：
`https://docs.google.com/spreadsheets/d/`**`1AbCd...XyZ`**`/edit`
中間粗體那一段就是 **試算表 ID**，等一下要用。

分頁不用自己開，腳本會自動建出兩個分頁：「Email訂閱名單」「作答結果」。（「組合統計（for稀有度計算）」10-05 起是試算表公式，腳本不碰它。）**在試算表裡改分頁名稱，要同步改 Code.gs 開頭的 TAB_ 常數**，不然腳本找不到分頁會自己再開一個舊名的新分頁，資料就寫到那裡去。

### 2. 貼程式

在那份試算表裡：**擴充功能 → Apps Script**。
把編輯器裡原本的 `function myFunction() {}` 全部刪掉，
貼上 `backend/Code.gs` 的全部內容。

第 21 行：
```js
const SHEET_ID = 'PASTE_SPREADSHEET_ID_HERE';
```
把引號裡換成剛剛那段 ID。存檔（Cmd+S）。

### 3. 先跑一次 setup

編輯器上方的函式下拉選單本來就會停在 **`setup`**（它是 `Code.gs` 裡第一個
定義的函式，下拉選單預設選第一個），直接按 **執行**。

第一次會跳授權：選你的 Google 帳號 → 「進階」→「前往（不安全）」→ 允許。
**這個警告是正常的**，因為這支腳本是你自己寫的、沒有經過 Google 審查。
跑完回試算表看，三個分頁應該都出現了。

### 4. 部署成網頁應用程式

右上角 **部署 → 新增部署作業** → 齒輪選 **網頁應用程式**：

| 欄位 | 要選什麼 |
|---|---|
| 執行身分 | **我**（`你的帳號`） |
| 具有存取權的使用者 | **所有人** |

> 「所有人」是必要的——測驗站的訪客沒有 Google 帳號也要能送出 email。
> 他們只能呼叫這支腳本，看不到試算表本身。

按部署，複製那串 **網頁應用程式網址**，`/exec` 結尾。

### 5. 填進網站

`web/scripts/config.js`：
```js
export const API_ENDPOINT = "https://script.google.com/macros/s/AKfy.../exec";
export const USE_LIVE_STATS = false;
```

`USE_LIVE_STATS` 先留 `false`：開站初期樣本本來就不到 300 筆，
稀有度會走估計值，這時候記錄作答只是白白消耗額度。
等站上跑一陣子、想開始看真實分布，再改成 `true`。

### 6. 測一次

打開測驗站走完三題，在結果頁填一個自己的 email 送出。
回試算表看「Email訂閱名單」分頁，應該多一列：時間 / email / 組合 / 來源。

## 三個會踩到的坑

**改完程式一定要「管理部署作業 → 編輯 → 版本：新版本」再部署。**
只按存檔，線上跑的還是舊的。這是 Apps Script 最常見的鬼打牆。

**Content-Type 一定是 `text/plain`，不能是 `application/json`。**
Apps Script 不會回應瀏覽器的 CORS 預檢請求；送 json 會先發一個 OPTIONS
然後整個失敗。前端 `signup.js` / `stats.js` 已經照這個規則寫了，別改回去。

**10-05 起作答結果可以手動刪列。** 稀有度直接數「作答結果」，刪掉的那筆就不算了
（最多 60 秒後生效）。「組合統計」分頁是公式，也會自己跟著變。

### 用 curl 測的時候會看到的假錯誤

`curl -L -X POST` 打 `/exec` 會回一頁「很抱歉，目前無法開啟這個檔案」的 HTML。
**那不是失敗**——Apps Script 會 302 轉到 `googleusercontent.com`，curl 跟著轉的時候
把 POST 的內容丟掉了，但腳本那一邊其實已經跑完、資料也寫進去了。
要確認有沒有成功，去看試算表，或再打一次 GET 看數字有沒有變。
瀏覽器的 `fetch` 不會有這個問題。

### 「送出失敗」其實有送成功（09-29 修掉）

Apps Script 收到 POST 會先把程式跑完、寫進試算表，才回 302 轉到
googleusercontent.com 拿結果。那一頁偶爾會 404、卡 26 秒、甚至回錯的內容
（實測十幾次壞三次，**三次資料都有進去**）。前端改成 `redirect: "manual"`：
拿到轉址就算成功，不去讀那一頁。讀稀有度的 GET 還是要讀那一頁，所以有 2.5 秒上限。

## 流量承受度（10-06 實測）

| 哪一段 | 測了什麼 | 結果 | 上限在哪 |
|---|---|---|---|
| 網頁本身（Cloudflare 靜態檔） | 測試站首頁同時 100 個、共 1,000 次 | 全部成功，中位數 0.17 秒 | 靜態檔不算 Worker 次數、不限量 |

| /api（Cloudflare Worker） | 同時 50 個讀統計表 | 全部成功 | **免費方案一天 10 萬次 Worker、10 萬次 Durable Object**，台北時間早上 8 點歸零 |

**每個訪客大約用掉：** Worker 4～5 次、Durable Object 5～6 次 → 免費方案**一天大約 1.5 萬個訪客**就到頂。
超過的話：網頁照樣打得開、可以玩，但**作答和 email 寫不進去**（email 會顯示「送出失敗」），稀有度改用估計值。
預期 12/1 一天會超過 1 萬人，就先升級 Workers Paid（每月 5 美元，一個月 1,000 萬次）。

**同一個 IP 的上限：** 每分鐘作答 20 筆、email 5 筆。手機網路常常很多人共用一個對外 IP，
12/1 如果在活動現場（大家連同一個 Wi-Fi）推，這個數字可能不夠，要先調 worker/api.js 的 `PER_MINUTE`。
